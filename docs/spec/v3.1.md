## Ключевые изменения v3 (кратко)

1. **VLM убран из Lite-профиля.** Бюджет CPU для 2B Q4 исправлен с «1–4 с/кадр» на **10–25 с/кадр**; GPU-бюджеты тоже пересчитаны честно (**1–4 с/кадр** для 2B), потому что доминирует стоимость vision-encode, а не декодирования (§8.2, §8.3).
2. **На CPU-only VLM — не кнопка в основном сценарии, а явная фоновая «ночная задача»** (experimental) с расчётным ETA, питанием от сети и мгновенной остановкой (§8.3.3).
3. **Только `*-Instruct`-сборки VLM**, thinking принудительно выключен, лимит выходных токенов и визуальных токенов, кэш по `hash + model_rev + prompt_rev` (§8.3.2, §8.4, D13).
4. **`VectorIndex` — интерфейс сменного бэкенда.** sqlite-vec — brute-force, комфортная зона до ~50–100K векторов; выше — ANN (usearch/HNSW) или гибрид «FTS5-сужение + точный реранк». Деградация до FTS5 **видима в UI**, а не тихая (§5.3, §6.2, §7, ADR-0004).
5. **PyInstaller one-dir вместо one-file**, target-triple suffix в имени sidecar, `RunEvent::Exit → kill children`, Job Object / process group / PDEATHSIG, watchdog на смерть родителя, тесты на осиротевшие процессы (§11.2, ADR-0005).
6. **Лицензионный гейт разделён на «код» и «веса»**: отдельный CI-job по манифесту моделей, fail-closed на неизвестной лицензии, проверка конкретного чекпойнта Qwen3-VL на M0 (§12).
7. **Песочница: единая политика для native и Docker.** Security-корпус обязан прогоняться нативно на 3 ОС; Docker-прогон — research-only и не заменяет нативный (§13.4).
8. **M0 получил три блокирующих спайка и гейты** (sqlite-vec/KNN, sidecar-lifecycle, PyInstaller one-dir), а также проверку двух главных рисков первыми (§14).
9. **Риски переранжированы:** топ-2 — производительность VLM на слабом железе и масштабирование векторного поиска (§17).

## 1. Общие сведения и позиционирование

**Продукт:** кроссплатформенное десктопное приложение для автоматической **раскладки** медиаархива (фото/видео/аудио) по пользовательским правилам и **каталогизации** библиотеки с оффлайн-AI-разметкой.

**Обещание пользователю:**
> «Разберёт архив из 200 000 файлов по папкам, которые вы задали, найдёт дубли, подпишет содержимое и сделает библиотеку поисковой. Всё локально. Ничего не удаляет и не портит — любую раскладку можно откатить одной кнопкой.»

**Три опоры продукта (в порядке важности для аудитории):**
1. Предсказуемость и сохранность данных (dry-run, журнал, undo, оригиналы неизменны).
2. Скорость разбора больших архивов.
3. Умная разметка и семантический поиск — то, чего нет у PhotoMove Pro и аналогов.

**Уточнение v3 (честность обещания).** Обещание выше относится к **раскладке, дублям и поиску** — они работают на любом профиле, включая Lite. **Генеративные описания (VLM) — не часть базового обещания**: на машинах без GPU они доступны только как отдельная длительная фоновая задача (§8.3.3). Формулировки в маркетинге, UI и `BETA_GUIDE.md` обязаны соответствовать этому разделению; «подпишет содержимое» на CPU-only означает теги/OCR/поиск, а не подписи VLM.

**Research-трек MIAS:** параллельно ведём threat modeling мультимодального пайплайна, red-team корпус, защитный контур и публичный разбор (`SECURITY_NOTES.md`). Требования безопасности — не «исследовательская надстройка», а обязательные требования продукта (§9).

**Отличие от v2:** v2 был архитектурно верен, но содержал оптимистичные цифры производительности VLM и трактовал sqlite-vec как готовый ANN-слой. v3 исправляет бюджеты, вводит сменный векторный бэкенд, ужесточает требования к упаковке/завершению sidecar и разделяет лицензионный контроль кода и весов.

## 2. Принятые решения

| ID | Решение | Обоснование | ADR |
|---|---|---|---|
| D1 | **Дистрибуция: Tauri 2 + Python-sidecar**, нативные установщики Win/macOS/Linux. Docker — только для разработки, CI и опционального NAS-режима (P2) | Docker непригоден для массовой аудитории: WSL2/виртуализация, overhead, нет Metal на macOS, нет интеграции с ОС | [ADR-0001](../adr/ADR-0001-distribution-tauri-sidecar.md) |
| D2 | **Профили качества Lite / Balanced / Pro с авто-детектом железа.** Ядро работает без GPU и без VLM. **Lite — без VLM** (ред. 2 в v3) | Продукт не должен деградировать до бесполезности на обычном ноутбуке; VLM на CPU — десятки секунд на кадр | [ADR-0002](../adr/ADR-0002-quality-profiles.md) |
| D3 | **Copy + XMP-sidecar по умолчанию. Оригиналы не изменяются и не удаляются.** Move, embedded-запись и запись в «свойства ОС» — opt-in | Доверие фотографа — главный барьер adoption; RAW внутрь не пишем никогда | [ADR-0003](../adr/ADR-0003-file-metadata-safety.md) |
| D4 | **ML-рантайм: ONNX Runtime + встроенный llama.cpp (GGUF).** Ollama — опциональное подключение внешнего сервера, не зависимость | Убрать «поставьте ещё пять программ» из первого запуска | ADR-0001 §Решение |
| D5 | **Только `safetensors`/GGUF, `trust_remote_code=False`, пиннинг ревизий + sha256** | pickle-веса = RCE (T08) | §9 SEC-08 |
| D6 | **Никаких LLM-агентов с инструментами** в пайплайне обработки медиа | Превращает prompt injection в действие на ФС/сети | §9 SEC-01/02 |
| D7 | Следующий шаг — **этот документ (ТЗ v3)**, затем M0 (спайки + замеры) / M1 (движок сортировки) | Ядро продукта не зависит от ML и от упаковки | §14 |
| **D8** | **VLM вне Lite.** На CPU-only — только явная фоновая задача «Ночная обработка» (experimental) с честным ETA; автозапуск и «улучшить описания» в основном потоке на CPU запрещены. Бюджеты §8.3 пересчитаны: CPU 2B Q4 — 10–25 с/кадр | Внешние замеры: ~18–19 с на кадр (4 ядра CPU) против обещанных 1–4 с; провал первого опыта важнее «красивой» цифры | ADR-0002 (ред. 2), §8.2–8.3 |
| **D9** | **`VectorIndex` — интерфейс сменного бэкенда.** M0: sqlite-vec (brute-force). Порог ~50–100K векторов → ANN (usearch/HNSW) или гибрид «FTS5-сужение + точный реранк». Деградация до FTS5 всегда видима | sqlite-vec 0.1.x — brute-force без ANN, ломающие изменения синтаксиса KNN, зависимость от `enable_load_extension`; целевой архив 200K+ | [ADR-0004](../adr/ADR-0004-vector-index-backend.md) |
| **D10** | **Упаковка sidecar: PyInstaller one-dir (не `-F`) + явный lifecycle.** Target-triple suffix, `RunEvent::Exit → kill children`, Job Object / process group / PDEATHSIG, watchdog | one-file распаковывается при каждом старте; PID бутлоадера ≠ PID Python → «висящие» процессы после закрытия | [ADR-0005](../adr/ADR-0005-sidecar-packaging-lifecycle.md) |
| **D11** | **Лицензионный гейт разделён: «код» и «веса».** Отдельный CI-job валидирует манифест моделей; неизвестная лицензия = fail-closed | Веса могут быть NC/research-only при «открытом» репозитории; это дороже переделывать после релиза | §12, SEC-08 |
| **D12** | **Единая политика песочницы для native и research-Docker**, генерируемая из одного файла. Security-метрики продукта считаются только по нативным прогонам на 3 ОС | Иначе security-тесты в Docker не воспроизводят условия Windows/macOS | §13.4 |
| **D13** | **В продуктовом пайплайне только `*-Instruct` VLM**, thinking выключен принудительно, лимит выходных токенов и визуальных токенов | Thinking-сборка тратит бюджет на рассуждения даже при коротком JSON-ответе | §8.3.2, §8.4 |

## 3. Целевая аудитория и сценарии

| Персона | Архив | Ключевой сценарий | «Магия» |
|---|---|---|---|
| Свадебный/репортажный фотограф | 100–500k файлов, RAW+JPEG, карты памяти | ingest → раскладка по съёмкам → отбор → сдача | группировка по съёмкам (время+гео+камера), отбор лучшего из серии, поиск «невеста с букетом» |
| Видеограф | 1–20 ТБ, MP4/MOV/BRAW | разложить по проектам, найти дубль | поиск по произнесённой фразе с тайм-кодом, авто-обложка, «дрон/интервью/B-roll» |
| Энтузиаст / семейный архив | 20–80k, телефон + скриншоты | «сделай порядок» | даты/события, дубли из мессенджеров, «скриншоты отдельно», лица (opt-in) |
| **Владелец большого архива на слабом ноутбуке** | 200k+, CPU-only, 8 ГБ | «сделай порядок и дай поиск» | раскладка + дубли + семантический поиск **без VLM**; ночная задача — по желанию |
| AI Security специалист (research) | — | воспроизвести атаки и защиты | red-team корпус, метрики ASR до/после, `SECURITY_NOTES.md` |

**Следствие для архитектуры (v3):** архив 200 000+ файлов означает 200 000+ векторов (плюс ключевые кадры видео). Это **выходит за комфортную зону brute-force sqlite-vec**, поэтому масштабирование поиска — требование P0, а не «оптимизация потом» (FR-3.13, NFR-18, ADR-0004).

**Основной пользовательский путь (happy path, ≤ 10 минут от установки):**
установил → перетащил папку → профиль определён автоматически → фоновая индексация с прогрессом → галерея + предложенные пресеты раскладки → **предпросмотр дерева «что куда»** → «Применить (копировать)» → при желании «Откатить».

На Lite этот путь **не включает VLM** и не требует загрузки VLM-весов.

## 4. Скоуп: P0 / P1 / P2 / Never

### P0 — обязательно для v0.1
- Сканер ФС + каталог SQLite, возобновляемая индексация, идемпотентность по контент-хэшу.
- Метаданные L0: EXIF/XMP/IPTC/QuickTime/ID3, иерархия источников даты + `date_confidence`.
- Движок правил: DSL, шаблоны путей, dry-run, план, транзакционное исполнение, **undo**, отчёт.
- Группировка ассетов (RAW+JPEG, sidecar'ы, Live Photo, burst).
- Точные дубли (blake3) + pHash-кандидаты в ревью, **группы дублей** (FR-2.14).
- AI-lite: эмбеддинги (SigLIP/OpenCLIP ONNX), zero-shot теги, семантический поиск текстом и по примеру, OCR.
- **`VectorIndex` за интерфейсом + масштабирование до 200K+ векторов + видимый статус деградации** (FR-3.13).
- Запись XMP-sidecar, экспорт/импорт XMP, пресеты приватности.
- Каталогизатор: галерея, фильтры/фасеты, полнотекстовый поиск, ручная правка тегов, **Review inbox**, редактор правил, Jobs.
- Профили Lite/Balanced/Pro + авто-детект; менеджер моделей (докачка, sha256, оффлайн-бандл, **лицензии весов**).
- **Корректная упаковка и завершение sidecar: one-dir, отсутствие осиротевших процессов** (§11.2).
- Установщики 3 ОС, подпись/нотаризация, автообновление (**NFR-21**), crash-report opt-in (**NFR-22**).
- Защитный контур SEC-01…SEC-17 (P0-подмножество §9), security-регрессия в CI **нативно на 3 ОС**.
- **M0-спайки как блокирующий гейт** (§14) и `KNOWN_LIMITATIONS.md` (§16).

### P1 — целевое для беты, допускаются флаги «experimental»
- VLM: подписи + структурированный JSON, keywords для стоков, alt-text — **только Balanced/Pro**; на CPU-only — отдельная ночная задача (experimental, D8).
- Видео: scene-cut, ключевые кадры, агрегация, обложка, тип контента.
- Аудио/видео: ASR (faster-whisper) + тайм-коды, SRT/VTT sidecar, поиск по речи.
- Почти-дубли (эмбеддинги + геометрическая проверка), выбор лучшего кадра в серии.
- Лица: детект + кластеризация персон **без имён**, opt-in, с согласием; **лицензия весов проверена до включения** (§12.2).
- Умные папки, карта, таймлайн, watch-режим (инкрементальная индексация).
- Персонализация: linear probe на правках пользователя.
- Технические метрики качества кадра (резкость/экспозиция/шум).

### P2 — после v0.1
Диаризация, авто-хайлайты, авто-чаптеры, эстетический скоринг, палитра/поиск по цвету, интеграции Lightroom/Capture One/digiKam, NAS/Docker-режим, шифрование каталога (SQLCipher), плагины/пресеты сообщества, многопользовательский режим, поиск по эскизу, VLM 8B (Pro+).

### Never (осознанные запреты)
Авто-удаление файлов; авто-перезапись оригиналов; облако по умолчанию; LLM-агент с инструментами (shell/HTTP/ФС) внутри обработки медиа; определение эмоций/расы/пола/возраста/привлекательности; скрытая телеметрия с содержимым; генеративная дорисовка изображений.

**Добавлено в v3:**
- Автозапуск VLM на CPU-only и на батарее; VLM в составе Lite-профиля.
- Thinking-сборки VLM в продуктовом пайплайне.
- «Тихая» деградация семантического поиска до FTS5 без индикации в UI.
- Обещание «1–4 с/кадр» (или любой другой не подтверждённой замером цифры) в UI, маркетинге и документации.
- PyInstaller `-F` (one-file) в релизной сборке.
- Публикация security-метрик продукта, полученных только в Docker.

#### 5.2.1 Канонический пример правил

```yaml
version: 1
library_root: "/media/Photo"
safety:
  mode: copy              # copy | move | hardlink
  verify: blake3
  never_delete: true
  keep_sidecars: true
  collision: suffix
rules:
  - id: docs_and_screens
    stop: true
    when:
      all:
        - ai.scene_type: { in: [document, receipt, whiteboard, screenshot] }
        - ai.confidence: { gte: 0.75 }
    then:
      path: "Docs/{date:%Y}/{ai.doc_kind|unknown}"
      tags: ["документ"]
  - id: jobs
    when:
      all:
        - ai.event_type: { in: [wedding, concert, sport] }
        - date: { between: ["2025-05-01", "2025-10-31"] }
    then:
      path: "Jobs/{date:%Y-%m-%d} {ai.event_type}/{camera.model|unknown}"
  - id: default
    then:
      path: "Archive/{date:%Y/%Y-%m-%d}/{kind}"
fallback:
  path: "_Unsorted/{file.mtime:%Y-%m}"
  review: true
```

#### 5.2.2 Токены шаблона пути (закрытый список)

`{date:FMT}` `{date.source}` `{camera.make}` `{camera.model}` `{lens}` `{iso}` `{kind}` `{ext}` `{ai.scene_type}` `{ai.event_type}` `{ai.doc_kind}` `{person.primary}` `{geo.country}` `{geo.city}` `{dup.group}` `{file.stem}` `{hash:8}` `{counter}`.
`{ai.caption_short}` — **запрещён по умолчанию**, доступен только с флагом `allow_free_text_paths: true` и усиленной санитизацией.

#### 5.2.3 Семантика токенов (v3.1, нормативно)

Закрытый список §5.2.2 не определял, что попадает в путь и что делать при отсутствии значения. Нормативно:

| Токен | Источник | Значение по умолчанию / ограничение |
|---|---|---|
| `{date:FMT}` | `taken_at` по иерархии FR-1.4, формат strftime | при отсутствии даты — `mtime` + review-бейдж «дата из mtime» |
| `{date.source}` | `taken_at_source` (exif/xmp/quicktime/id3/filename/mtime) | `unknown` |
| `{camera.make}`, `{camera.model}` | EXIF Make/Model; нормализация: пробелы → `_`, обрезка до 40 символов | `unknown` |
| `{lens}`, `{iso}` | EXIF LensModel / ISO | `unknown` |
| `{kind}` | photo · raw · video · audio · sidecar | всегда есть |
| `{ext}` | расширение без точки, нижний регистр | всегда есть |
| `{ai.scene_type}`, `{ai.event_type}`, `{ai.doc_kind}` | закрытые словари §8.4, только при уверенности выше порога профиля | `unknown`; при деградации AI — `unknown` без блокировки (FR-2.13) |
| `{person.primary}` | имя первичной персоны (FR-3.9) — **только после явного именования пользователем** | `nobody`; сгенерированные кластеры в путь не попадают никогда |
| `{geo.country}`, `{geo.city}` | EXIF GPS + оффлайн-справочник | `unknown`; при пресете `stock` возвращают `unknown` (SEC-04) |
| `{dup.group}` | группа дублей FR-2.14 | `single` если у ассета нет копий; `exact-<hash8>` если у ассета несколько файлов с одинаковым `content_hash` |
| `{file.stem}` | имя файла без расширения, полная санитизация | `file` |
| `{file.mtime:%Y-%m}` | mtime файла, формат strftime (как в примере §5.2.1) | — |
| `{hash:N}` | префикс `content_hash` длиной N (по умолчанию 8) | — |
| `{counter}` | порядковый номер в пределах правила, 1-based, стабилен внутри плана | — |

## 6. Архитектура и технологический стек

### 6.1 Процессы

```
UI Shell (Tauri 2, системный webview)
   ↕ IPC + HTTP с bearer-токеном, только 127.0.0.1, случайный порт
Engine API (Python 3.12, FastAPI): каталог, правила/планы/undo, jobs, превью, экспорт
   │   └── VectorIndex (интерфейс) → sqlite-vec | ANN (usearch/HNSW) | hybrid (FTS5 + rerank)
   ↕ локальный IPC (очередь задач в SQLite)
Worker pool (отдельные процессы, песочница, rlimits, таймауты):
   • parser-worker: exiftool / libvips / Pillow / rawpy / ffmpeg  ← недоверенный вход
   • ai-worker: ONNX Runtime (эмбеддинги, OCR, детекторы)
   • vlm-worker: llama.cpp server (GGUF) — запускается по требованию, не резидент
Model store: <appdata>/models (манифест, sha256, версии, лицензии, докачка)
```

**Инварианты архитектуры:**
- Падение/компромисс воркера не роняет UI и не портит каталог.
- Воркеры не имеют сети и не имеют доступа к ФС вне песочницы.
- Engine умеет работать как CLI и как локальный сервер (для тестов, research и будущего NAS-режима).
- Единственный путь к ФС-мутациям — исполнитель утверждённого плана.
- **Дерево процессов принадлежит оболочке (v3):** любой процесс, порождённый sidecar (включая «внуков» — exiftool, ffmpeg, llama-server), входит в ту же Job Object / process group и гарантированно завершается при выходе приложения (§11.2).
- **vlm-worker не резидентен (v3):** поднимается на время задачи, освобождает память после; отсутствие VLM не влияет на остальной пайплайн.
- **Доступ к векторному индексу — только через `VectorIndex` (v3):** домен не знает, какой бэкенд внутри.

## 7. Модель данных

Источник истины — каталог SQLite; файлы — производные. Полный DDL фиксируется в `kadr/catalog/schema.sql` на M0 (путь исправлен в v3.1: в v3 ошибочно указывался `engine/catalog/schema.sql`). Обязательные сущности:

| Таблица | Назначение / ключевые поля |
|---|---|
| `volumes` | uuid, label, root_path, last_seen (съёмные диски, NAS) |
| `assets` | content_hash, kind, bytes, w/h, duration_ms, taken_at, **taken_at_source**, date_confidence, tz, camera_*, gps_*, phash, quality_json |
| `files` | asset_id, volume_id, rel_path, ext, mtime, is_primary, exists_flag (ассет = несколько файлов) |
| `meta_raw` | asset_id, tool, tool_version, **json (immutable)** — сырой дамп, чтобы переигрывать обработку без чтения диска |
| `ai` | asset_id, task, **model_id, model_rev, prompt_rev**, output_json, confidence, created_at, **runtime_ms, device** (для калибровки ETA) |
| `tags` / `asset_tags` | иерархия + синонимы RU/EN; **source (model/user/import), confidence, verified_by** |
| `faces` / `persons` | bbox, embedding, cluster_id; consent_flag (opt-in) |
| `embeddings` | asset_id, model_id, **dim, index_generation**, vec (float16 / int8 / bit) — источник истины для любого бэкенда индекса |
| **`vector_index_state`** | backend (`sqlite-vec`/`ann`/`hybrid`), index_generation, vector_count, dim, quantization, built_at, build_progress, **status (active/building/degraded/unavailable)**, reason, measured_p95_ms |
| **`device_bench`** | device_id, os, cores, ram, gpu, task, model_rev, ms_per_item, measured_at — цифры для ETA и профиля (не константы в коде) |
| `fts` | caption, ocr_text, asr_text (FTS5, ru+en) |
| `collections` | static / smart (query_json) |
| `rules` | ord, yaml, enabled, version |
| `plans` / `plan_items` | режим, summary, state; src→dst, action, state, error |
| `journal` | plan_id, seq, action, src, dst, hash, done_at, undone_at (write-ahead) |
| `review_queue` | reason, severity, payload_json, state |
| `jobs` | kind, state, progress, error, timestamps, **eta_seconds, throttle_reason** |
| `settings` | k, v (профиль, политика безопасности, приватность, **vector_backend_override, nightly_vlm_enabled**) |

**Требования:** WAL, миграции (версионирование схемы), права 0600 на каталог, исключение из облачной синхронизации, `VACUUM`/`ANALYZE` по расписанию, бэкап каталога перед массовыми операциями.

**Дополнено в v3:**
- Векторы хранятся в `embeddings` **независимо** от индекса: смена бэкенда = пересборка индекса, а не пересчёт эмбеддингов (дорогая операция не повторяется).
- `vector_index_state.status` — единственный источник правды для UI-бейджа поиска; значение `degraded/unavailable` обязано иметь `reason` (расширение не загрузилось, идёт сборка, превышен порог).
- Размер индекса и квантование фиксируются: float16 по умолчанию, int8/bit — по профилю и результату замера recall (потеря качества измеряется на golden, а не предполагается).
- `device_bench` заполняется замером на 20 файлах (§8.3.1) и обновляется при смене железа/драйвера/версии рантайма.

**Дополнено в v3.1:**
- `fts` и `fts_fallback` создаются не в `schema.sql`, а в `catalog.repository._ensure_fts()` (идемпотентно, при старте). Допустимо; требование — идемпотентность и тест «FTS5 доступен / видимый fallback».

## 8. AI-подсистема и профили качества

### 8.1 Уровни обработки

L0 метаданные → L1 дешёвые CV-сигналы → L2 эмбеддинги → L3 специализированные модели (OCR/ASR/детекторы) → L4 VLM. Каскад: переход на следующий уровень только при необходимости (низкая уверенность / требование правила / профиль).

**v3:** уровень **L4 не входит в Lite** и не запускается автоматически на CPU-only. Ценность продукта на слабом железе строится на L0–L3; L4 — опциональное «улучшение по запросу», в том числе как ночная задача (§8.3.3).

### 8.2 Авто-детект профиля (D2)

Определяем: RAM, число физических ядер, наличие GPU/VRAM (CUDA/DirectML), Apple Silicon + unified memory, свободное место, питание (батарея/сеть), **поддержку загрузки расширений SQLite** (для векторного поиска).

| Условие | Профиль | Состав |
|---|---|---|
| RAM < 8 ГБ или ядер < 4 | **Lite (forced)** | L0+L1+L2 (int8), OCR по требованию. **VLM недоступен** (не предлагается, не скачивается) |
| RAM ≥ 8 ГБ, CPU без GPU | **Lite** | L0+L1+L2, OCR, семантический поиск. **VLM в профиле нет.** Отдельно доступна experimental-задача «Ночная обработка (VLM)» (§8.3.3) с расчётным ETA и предупреждением |
| Apple Silicon, ≥ 16 ГБ unified | **Balanced** | + VLM 2B Instruct (Metal), ASR small |
| Дискретная GPU ≥ 6 ГБ VRAM и RAM ≥ 16 ГБ | **Pro** | + VLM 4B Instruct, ASR turbo, лица, почти-дубли, видео-аналитика |
| RAM ≥ 32 ГБ и VRAM ≥ 12 ГБ | Pro+ (P2) | VLM 8B Instruct |

**Изменение против v2 (замечание №1 ревью).** Строка «Lite + предложение Balanced: VLM 2B Q4 включается кнопкой "Улучшить описания"» **удалена**. На CPU-only нет кнопки, обещающей быстрый результат: есть отдельная длительная задача с честной оценкой времени. Это приводит документ в соответствие с ADR-0002 («Lite — без VLM»).

Профиль виден в UI и переопределяем; на батарее — сниженный параллелизм и запрет авто-запуска VLM. Перед включением профиля показываем размер загрузки и **замеренную на этом устройстве** скорость (20 файлов), а не табличные константы.

### 8.3 Бюджеты моделей (исправлено в v3)

> **Нормативно:** приведённые цифры — **ожидания для планирования, а не обещание**. Единственный источник цифр, которые видит пользователь, — `docs/BENCHMARKS.md` и таблица `device_bench` (замер на устройстве). Расхождение факта с таблицей > 2× — повод обновить таблицу и UI-тексты, а не «оптимизировать бенчмарк».

> **Единый запрет цифр (v3.1, распространяется на все разделы, включая §11.4 и маркетинг):** ни одна цифра скорости (VLM, эмбеддинги, OCR, ASR, латентность поиска) не попадает в UI, мастер первого запуска, README, `BETA_GUIDE.md` и маркетинговые материалы без строки-источника в `docs/BENCHMARKS.md` или записи `device_bench`. До прохождения спайка D допустимы только пометки «не измерено» и диапазон с явной подписью «ожидание».

| Компонент | Размер | Скорость (ожидание, ⚠️ подтвердить замером M0) |
|---|---|---|
| Эмбеддинги int8 ONNX | 150–400 МБ | 10–25 фото/с (8 ядер CPU); 3–8 фото/с (4 ядра) |
| OCR ONNX | 20–80 МБ | 2–6 фото/с |
| Face detector (P1) | 5–20 МБ | ≥ 15 фото/с |
| ASR small / turbo (P1) | 250 МБ / 800 МБ | ≥ 5× / ≥ 2× realtime CPU |
| **VLM 2B Q4 Instruct + mmproj** | 1.5–2 ГБ + 0.3–0.6 ГБ | **CPU 4 ядра: 15–25 с/кадр; CPU 8 ядер: 10–18 с/кадр**; Metal/CUDA: **1–4 с/кадр**; повторный вопрос по тому же кадру (KV/image-embeds в кэше): 0.1–0.6 с |
| **VLM 4B Q4 Instruct (Pro)** | 2.5–3 ГБ + mmproj | **GPU: 2–6 с/кадр**; CPU — вне профиля (не поддерживается как продуктовый сценарий) |

**Что именно исправлено и почему:**

1. **CPU 2B: «1–4 с/кадр» → «10–25 с/кадр».** Внешние замеры дают ~18–19 с на обработку одного нового кадра Qwen3-VL-2B на четырёхъядерном CPU. Заявленная в v2 цифра была занижена в разы и разрушила бы первый опыт пользователя Lite.
2. **GPU тоже пересчитан: «0.3–1 с» → «1–4 с».** Узкое место — **vision-encode (prefill по визуальным токенам)**, а не генерация текста: в публичных замерах Qwen3-VL-2B forward с картинками измеряется секундами даже на топовых GPU, тогда как без картинки — сотнями миллисекунд и меньше. Follow-up по уже закодированному кадру действительно дешёвый — это и создавало иллюзию «0.3 с».
3. **4B на слабом ноутбуке — не сценарий.** На i5 8-го поколения / 8 ГБ задержка «заметно тормозит»; 4B остаётся только в Pro с дискретной GPU.
4. **Дешёвый повторный вопрос ≠ дешёвый новый кадр.** В продукте почти все вызовы — новый кадр, поэтому в бюджете и ETA используется стоимость **нового кадра**.

#### 8.3.1 Как считаем и показываем ETA (нормативно)

- Модель стоимости: `T ≈ N_кадров × t_encode(устройство, разрешение) + N_выходных_токенов × t_decode`. Для видео `N_кадров = Σ K(сцен)` по всем роликам.
- `t_encode` берётся из замера на 20 репрезентативных файлах (`kadr bench`) при выборе профиля и сохраняется в `device_bench`; пересчитывается при смене версии рантайма/модели/железа.
- UI показывает **диапазон и порядковую величину**, а не точность до минуты: «≈ 18 с на фото · 1 200 фото ≈ 6 часов».
- Точность ETA — требование NFR-19: отклонение факта от прогноза ≤ ±30% после калибровки.
- Запрещено: показывать «ускорение» за счёт того, что часть кадров уже в кэше, без явной подписи «N из M уже обработано ранее».

#### 8.3.2 Требования к рантайму VLM (нормативно, P0 при включении VLM)

| Требование | Значение |
|---|---|
| Вариант модели | только `*-Instruct`; Thinking-сборки запрещены (D13); в манифесте поле `thinking: false` |
| Thinking-режим | принудительно выключен флагами рантайма/шаблона чата; если рантайм всё равно отдаёт reasoning-блоки — они отбрасываются, событие логируется как аномалия, кадр уходит в повтор с жёстким лимитом |
| Лимит выхода | `max_output_tokens` = 384 для JSON-контракта (§8.4); превышение → обрезка по grammar, а не свободная генерация |
| Визуальные токены | длинная сторона изображения ≤ 1024 px (Lite-ночь: ≤ 768 px), жёсткий cap визуальных токенов; замер на двух разрешениях обязателен |
| Кэш | по `hash + model_rev + prompt_rev + resolution`; повторный запуск не пересчитывает кадр |
| Параллелизм | не более `cores − 1` потоков; на батарее — запрет; при активности пользователя — throttle |
| Изоляция | vlm-worker в песочнице, без сети, без инструментов; завершается вместе с деревом процессов (§11.2) |
| Память | не резидентен; выгрузка модели после завершения задачи; NFR-06 действует и при активном VLM-джобе (пик фиксируется в замере) |
| Пиннинг | версия llama.cpp, ревизия GGUF и `mmproj` запинены + sha256; апгрейд — отдельное решение с повторным замером |

#### 8.3.3 Ночная задача VLM на CPU-only (experimental, D8)

**Условия доступности:** профиль Lite/CPU-only, пользователь явно включил задачу, питание от сети, свободно ≥ 4 ГБ RAM и ≥ 3 ГБ на диске под веса.

**Экран подтверждения (эталонный текст, RU):**
> «Улучшение описаний с помощью ИИ на этом компьютере работает медленно: **≈ 18 секунд на фото**. Для 1 200 фото это **≈ 6 часов**. Задача будет выполняться в фоне, пока компьютер подключён к питанию, и не помешает работе. Её можно остановить в любой момент — уже обработанные фото сохранятся. Раскладка, дубли и поиск работают и без этого.»

**Требования:**
1. Запуск — только явным действием; никогда автоматически, никогда при первом запуске, никогда на батарее.
2. Отдельный job с прогрессом, ETA, паузой, остановкой (отмена ≤ 1 с) и возобновлением после перезапуска приложения.
3. Окно тишины (по умолчанию 22:00–08:00, настраивается), авто-пауза при возврате пользователя к активной работе, при перегреве/троттлинге и при переходе на батарею.
4. Не блокирует UI, индексацию, поиск и применение планов; приоритет ниже интерактивных задач.
5. Результаты пишутся инкрементально (каждый кадр — отдельная транзакция), помечаются `source=model`, `experimental=true`.
6. Пометка experimental в UI и в `KNOWN_LIMITATIONS.md`; при отключении задачи уже полученные результаты остаются, ничего не удаляется.
7. Если замер показывает > 25 с/кадр — задача остаётся experimental и в UI предлагается только выборкой («обработать выделенные 200 фото»), а не всем архивом.

#### 8.3.4 Что обязан замерить M0 (блокирующий гейт)

- `t_encode` и `t_decode` для VLM 2B Q4 Instruct на: 4-ядерном CPU (8 ГБ), 8-ядерном CPU (16 ГБ), Apple Silicon (Metal), дискретной GPU ≥ 6 ГБ; два разрешения (768/1024 px); thinking on/off (для подтверждения, что off действительно работает).
- То же для 4B на GPU.
- Эмбеддинги/OCR/ASR — фото/с по тем же машинам.
- Результаты → `docs/BENCHMARKS.md` + `device_bench`; таблица §8.3 обновляется фактами; UI-тексты и ETA берутся из замера.

### 8.4 Контракт вывода VLM (нормативный)

Строгая JSON-схема, значения из закрытых словарей, валидация Pydantic, отбрасывание всего лишнего:

```json
{
  "scene_type": "wedding_ceremony",
  "setting": "outdoor_garden",
  "subjects": ["bride", "groom", "guests"],
  "actions": ["exchange_rings"],
  "event_type": "wedding",
  "time_of_day": "golden_hour",
  "weather": "clear",
  "lighting": "natural_backlight",
  "text_present": false,
  "quality_issues": [],
  "keywords_en": ["wedding", "ceremony", "rings", "garden"],
  "caption_ru": "Церемония обмена кольцами в саду на закате.",
  "confidence": 0.82
}
```

Требования: `prompt_rev` фиксирован и хранится; **в промпт не попадают метаданные, OCR и ASR** без явного opt-in; у модели нет инструментов; свободные текстовые поля (`caption_*`) проходят PII-фильтр и никогда не используются в путях по умолчанию.

**Добавлено в v3:** grammar-constrained decoding обязателен (не «попросить модель вернуть JSON»); `max_output_tokens` жёсткий; поля рассуждений/`thinking` в схеме отсутствуют и отбрасываются; при невалидном JSON — один повтор с укороченным промптом, затем `review`-флаг без записи в каталог; версия модели в манифесте — только Instruct (D13).

### 11.1 Артефакты

| ОС | Артефакт | Подпись |

| Windows | `.msi` (+ `.exe` NSIS при необходимости) | code signing: Azure Artifact Signing ≈ $9.99/мес (**для физлиц только США/Канада**, платная подписка Azure, не free/trial) либо OV-сертификат $150–300/год ([MS docs](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options)); репутация SmartScreen набирается скачиваниями — предупреждения возможны даже с подписью (фиксируется в `KNOWN_LIMITATIONS.md`) |

| Linux | `.AppImage` + `.deb` + `.rpm` | без подписи; тесты на X11/Wayland, glibc; **проверка загрузки sqlite-vec на каждом формате пакета** |

Автообновление: Tauri updater с подписанными манифестами, каналы `beta`/`stable`, возможность отложить (фотограф не обновляется посреди сдачи проекта). Обновление обязано проходить через тот же корректный shutdown дерева процессов (§11.2), иначе апдейт оставит старый Python-процесс на старом порту.

### 11.2 Sidecar-lifecycle (Tauri ↔ Python) — расширено в v3

Оболочка запускает Engine как дочерний процесс, получает случайный порт и токен через stdout-handshake/IPC, следит за живостью, корректно завершает при выходе (никаких «висящих» процессов), перезапускает при краше с уведомлением. Токен не попадает в URL и в логи. Dev-режим (`0.0.0.0`, без подписи) отделён конфигом и **не может попасть в релизную сборку** (CI-проверка).

#### 11.2.1 Упаковка (нормативно)

1. **Только PyInstaller one-dir.** `-F`/one-file запрещён в релизе: он распаковывается во временный каталог при **каждом** запуске (медленный старт) и создаёт пару «бутлоадер → Python», из-за которой PID запущенного бинаря ≠ PID интерпретатора; `kill` по этому PID оставляет Python живым. CI проверяет spec-файл на отсутствие one-file режима.
2. **Имя бинаря с target-triple suffix.** Tauri требует `binaries/kadr-engine-<target-triple>[.exe]`; суффикс берётся из `rustc --print host-tuple`. Без него сборка падает с `Failed to copy external binaries`. Скрипт переименования — в `packaging/`, CI проверяет наличие файла под каждый целевой таргет **до** сборки установщика.
3. **Capabilities.** Разрешение `shell:allow-execute` с `"sidecar": true` и точным именем; аргументы — по allowlist, без «true» (произвольные аргументы) в релизе.
4. **Fallback.** Если one-dir не даёт нужного старта/размера — Nuitka (решение фиксируется в ADR-0005 по факту замеров M0), а не возврат к one-file.

#### 11.2.2 Владение деревом процессов (нормативно)

| ОС | Механизм | Гарантия |
|---|---|---|
| Windows | Job Object с `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, все дети и внуки внутри job | убийство дерева даже при `kill -9` оболочки |
| Linux | новая process group (`setsid`/`start_new_session`) + `PR_SET_PDEATHSIG` в детях + kill по группе | нет «внуков», выходящих из-под контроля |
| macOS | process group + явный `killpg` в хуке выхода (PDEATHSIG отсутствует) | обязательный явный путь завершения, не полагаемся на смерть родителя |

Внуки (exiftool, ffmpeg, llama-server, ONNX-воркеры) обязаны порождаться внутри той же группы/job; список PID логируется (без PII) для диагностики.

#### 11.2.3 Последовательность завершения (единый путь для всех сценариев)

```
app_shutdown()                       # единственная точка выхода
  1. POST /internal/shutdown (bearer) → Engine: остановить воркеры, checkpoint WAL, flush журнала
  2. wait ≤ 2 с на exit(0)
  3. если жив: terminate group / TerminateJobObject
  4. wait ≤ 3 с → kill -9 group
  5. удалить lock/port-файл, освободить single-instance lock
```

> **Бюджет завершения (v3.1, нормативно).** Полный цикл `app_shutdown()` — **≤ 5 с**: шаг 2 (graceful) ≤ 2 с, шаги 3–4 (принудительное завершение группы) ≤ 3 с. Требование NFR-17 «0 процессов через ≤ 3 с» относится к шагу 3, а не ко всему циклу; это устраняет прежнее противоречие между §10 и §11.2.3.

Хуки: `RunEvent::ExitRequested` / `RunEvent::Exit` → `app_shutdown()`; **плюс** явный вызов из всех путей, которые могут миновать `RunEvent`.

| Edge case | Требование |
|---|---|
| Windows: `prevent_exit()` + `AppHandle::exit()` | завершение идёт через `app_shutdown()`, а не «просто exit»; Job Object — страховка |
| macOS: `MenuItem::Quit`, Cmd+Q, `applicationShouldTerminate` | перехватываем и вызываем тот же путь; нельзя полагаться только на `RunEvent` |
| Закрытие последнего окна / трей-quit | тот же путь |
| `kill -9` UI / краш webview | срабатывает Job Object (Win) / PDEATHSIG (Linux) / watchdog (macOS) |
| Watchdog в sidecar | закрытие stdin-pipe или отсутствие heartbeat > 5 с → самозавершение + убийство своих детей |
| Logout / reboot / shutdown ОС | обработка системного запроса завершения, ≤ 3 с |
| Обновление через updater | shutdown → замена файлов → старт; проверка, что старый процесс не держит порт |
| Двойной запуск | single-instance lock; второй экземпляр не поднимает второй Engine |

#### 11.2.4 Приёмочные тесты (v3.1: M0-минимум и полный набор)

**M0-минимум — блокирующий PR-гейт (3 сценария):**

1. `terminate_group` убивает новую process group / job вместе с sidecar;
2. single-instance lock не даёт второму экземпляру поднять второй Engine;
3. «внук» (дочерний процесс sidecar) умирает вместе с группой.

Для каждого: assert «0 процессов дерева, 0 handle'в к `library_root`, порт свободен» через **≤ 3 с после начала принудительного завершения**. Тест падает при любом осиротевшем процессе и входит в PR-гейт, а не только в nightly.

**Полный набор — релизный гейт M6:** все сценарии §11.2.3 на каждой ОС — `prevent_exit()+AppHandle::exit()`, `MenuItem::Quit`/Cmd+Q, kill -9 UI, logout/reboot, updater-restart, двойной запуск, watchdog на смерть родителя. Релиз без полного набора запрещён.

> **Статус на v3.1 (честно):** в репозитории реализованы 2 проверки из M0-минимума (группа + single-instance), причём проверка живости на Windows некорректна (`os.kill(pid, 0)`). Это BLK-02 отчёта о готовности; гейт красный до исправления.

### 11.3 Модели

Установщик без моделей → менеджер моделей в приложении: профиль, размеры, **замеренная** скорость (20 файлов), скачивание с возобновлением, sha256 (включая `mmproj`), зеркало, **оффлайн-бандл** одним файлом, индикатор «оффлайн». Проверка целостности при старте. Обновление модели — явное действие + diff-отчёт «что изменилось в разметке».

**Добавлено в v3:**
- Карточка модели показывает **лицензию, источник лицензии, дату проверки и разрешённые профили** (§12.2). Модель с непроверенной лицензией не скачивается.
- VLM-веса не предлагаются и не скачиваются на Lite автоматически; загрузка возможна только при явном включении ночной задачи, с показом размера и расчётного времени обработки.
- В манифесте фиксируется `variant: Instruct` и `thinking: false`; попытка подсунуть Thinking-сборку — ошибка валидации манифеста.
- Смена модели эмбеддингов запускает переиндексацию (`index_generation`, FR-3.15) с показом объёма работы и без потери поиска на время сборки.

### 11.4 Первый запуск (мастер)

1. Язык → 2. Перетащить папку/выбрать библиотеку → 3. Авто-профиль (объяснение, что будет скачано **и что не будет**: на Lite — «описания ИИ не входят, поиск и раскладка работают») → 4. Политика: **«Копировать, оригиналы не трогаем» (default)**, галочки «вписывать теги в файл», «показывать в свойствах ОС» → 5. Индексация с прогрессом → 6. Галерея + 3 пресета раскладки → 7. Предпросмотр → Применить → Undo всегда доступен.

Явно спрашиваем: «Есть ли у вас бэкап архива?» — и предлагаем начать с тестовой папки.

**Запрещено в мастере (v3.1):** обещать «умные подписи за секунды» на CPU-only; включать VLM по умолчанию; скачивать VLM-веса «на всякий случай»; скрывать факт деградации векторного поиска, если расширение не загрузилось; **показывать любую цифру скорости без строки-источника в `docs/BENCHMARKS.md`** (§8.3).

### 12.3 CI-гейты

| Job | Что проверяет | Условие падения |
|---|---|---|
| `license-code` | SBOM-diff, SPDX-выражения зависимостей (pip + cargo), lockfile integrity | новая зависимость с AGPL/NC/GPL-static в пользовательском профиле; неизвестная лицензия без явного исключения в `licenses/allowlist.yaml` (схема — §12.4) |
| **`license-weights`** | `models/manifest.yaml`: наличие и валидность `license`, `license_source_url`, `license_verified_at`, `commercial_use`, `allowed_profiles`, `revision`, `sha256` | лицензия ∈ {`AGPL-3.0*`, `CC-BY-NC-*`, `research-only`, `non-commercial`, `GPL-*`} для пользовательского профиля; `commercial_use: false`; пустой/просроченный `license_verified_at`; неизвестная лицензия; модель VLM с `allowed_profiles`, содержащим `lite`; `variant != Instruct` |
| `model-integrity` | sha256 всех файлов, включая `mmproj`, соответствие запиненной ревизии | любое расхождение |
| `sqlite-vec-smoke` | расширение загружается, `vec0` создаётся, KNN-запрос (`k = ?`) возвращает результат — **на всех 3 ОС и во всех форматах пакета** | падение загрузки или пустой результат (иначе поиск молча деградирует до FTS) |
| `sidecar-lifecycle` | сценарии §11.2.4 | любой осиротевший процесс |
| `sandbox-parity` | эффективность лимитов native vs research-Docker (§13.4) | расхождение политик |

Файлы `LICENSES.md` + `THIRD_PARTY_NOTICES.md` — в комплекте; лицензии весов перечисляются отдельно от лицензий кода.

### 12.4 `licenses/allowlist.yaml` (v3.1, нормативно)

Единственное место, где допускаются исключения для гейта `license-code`:

```yaml
schema_version: 1
reviewed_at: "2026-11-20"        # ISO-дата ревью
reviewed_by: "владелец продукта"
entries:
  - component: "package==1.2.3"  # точное имя и версия, не диапазон
    license: "LGPL-2.1-only"
    reason: "динамическая линковка, код не модифицируем"
    scope: "runtime"             # runtime | build | dev | research
    expires_at: "2027-05-20"     # обязательно, ≤ 12 месяцев
    issue: "https://github.com/…/issues/123"   # тикет на снятие
```

Правила: запись действует **только на точную версию**; отсутствие `expires_at` или истёкший срок — падение гейта; `scope: research` не распространяется на пользовательскую сборку; каждая запись обязана иметь тикет на снятие; ревьюер — владелец продукта; CI проверяет схему, срок и наличие тикета.

## 13. Тестирование и качество

**Пирамида:** unit (правила, санитизация, шаблоны, дата-иерархия) → integration (скан→анализ→план→apply→undo) → property-based (hypothesis на генераторе путей и правилах) → fault-injection (kill -9, ENOSPC, отвал тома, locked files) → e2e на 3 ОС (Playwright для UI) → security-регрессия (§9) → UX-прогон сценария.

### 13.1 M0-спайки (блокирующие, замечания №2, №3 и 🧭2 ревью)

| Спайк | Что проверяем | Критерий прохождения |
|---|---|---|
| **A. sqlite-vec / KNN** | загрузка расширения (`enable_load_extension`), создание `vec0`, KNN с `k = ?`, пиннинг версии, поведение в AppImage/deb/rpm/msi/dmg | на всех 3 ОС запрос возвращает корректный результат; при недоступности — UI показывает деградацию, FTS5 работает |
| **B. Sidecar-lifecycle** | все сценарии §11.2.3, включая `prevent_exit()+exit()` (Win), `MenuItem::Quit`/Cmd+Q (macOS), kill -9 UI, logout, updater-restart, «внуки» вне группы | 0 осиротевших процессов и 0 handle'в к библиотеке через ≤ 3 с |
| **C. PyInstaller one-dir** | холодный/повторный старт, размер, отсутствие распаковки, корректное завершение, антивирусы/SmartScreen | старт ≤ 2 с (NFR-16), нет «висящих» Python-процессов, размер в бюджете NFR-07 |
| **D. VLM-бюджеты** | §8.3.4 на 4 классах устройств, 2 разрешения, thinking on/off | таблица §8.3 заменена фактами; UI/ETA берут цифры из замера |
| **E. Масштаб поиска** | 50K / 100K / 200K / 500K синтетических векторов: p95, recall@10, размер БД, время сборки | выбран порог переключения бэкенда; NFR-18 достижим хотя бы одним бэкендом |

Порядок (v3.1, синхронизировано с §14): **D → E → A → B → C**. D и E — первыми, потому что это главные риски продукта (§17); спайк B выполняется уже в реальном Tauri-хосте (P1-07 плана), иначе проверяется не тот сценарий. Отрицательный результат любого спайка — не «продолжаем как есть», а решение по гейту §14.

### 13.2 Регрессия качества и производительности

**Golden-датасет:** 500–1000 файлов с ручной разметкой (сцены, события, качество, дубли, «злые» файлы), только свои/разрешённые материалы; версионируется; используется для регрессии качества и security.

#### 13.2.1 Протокол golden-датасета (v3.1, нормативно)

- **Состав:** 500–1000 файлов; ≥ 40% «трудных» (без EXIF, битые даты, HEIC/RAW, burst-серии, скриншоты, документы, 2–3 коротких видео); ≥ 10% adversarial из `security/corpus`.
- **Разметка:** сцена, событие, «уместная папка», качество кадра, дубли (точные/почти), «злые» файлы. Размечает владелец продукта, вслепую к выводу продукта.
- **Хранение:** файлы — вне git (LFS или внешний бакет); в репозитории — только `tests/golden/manifest.json` с хэшами, лицензиями и `source` каждого файла.
- **Лицензии материалов:** только собственные или разрешённые; файл без установленной лицензии в датасет не попадает.
- **Версии:** `golden-vN`; любая правка разметки — новая версия и запись в `docs/BENCHMARKS.md`.
- **Частота:** nightly — полный прогон; PR — подмножество ≤ 100 файлов (< 10 мин).
- **Владелец:** назначается до старта M2; без владельца гейт M2 не закрывается (§14).

**Метрики качества (цели к v0.1):**

| Метрика | Цель |
|---|---|
| Корректность раскладки «по дате» | ≥ 99% |
| Согласие пользователя с раскладкой «по контексту» | ≥ 75% |
| precision@5 автотегов (Lite / Balanced) | ≥ 0.70 / ≥ 0.80 |
| Точность точных дублей | 100% (никаких ложных) |
| Почти-дубли: recall / FPR | ≥ 0.90 / ≤ 2% |
| OCR CER на печатном тексте | ≤ 15% |
| Семантический поиск nDCG@10 | ≥ 0.60 |
| **recall@10 векторного индекса vs точный перебор** | **≥ 0.90 (при квантовании/ANN — измеряется, не предполагается)** |
| ASR WER (RU, чистая речь, small) | ≤ 25% |
| Ложные review-флаги | ≤ 5% |
| **Точность ETA VLM** | **±30% (NFR-19)** |

**CI matrix:** Windows/macOS/Linux × Python 3.12; nightly — полный golden-прогон, бенчмарки и scale-тесты; PR — быстрый набор (< 10 мин) + обязательные `sqlite-vec-smoke`, `sidecar-lifecycle`, `license-weights`.

VLM-метрики качества считаются только на Balanced/Pro-железе; отсутствие GPU в CI не должно маскировать регрессию — для неё выделяется self-hosted runner или ночной прогон на машине разработчика с публикацией результата.

### 13.3 Бенчмарк-харнесс

`kadr bench` — публичный харнесс: устройства, ОС, версии рантаймов, размеры моделей, фото/с и с/кадр, латентность поиска на 50K/100K/200K, размеры БД. Результаты — `docs/BENCHMARKS.md`, публикуются вместе с релизом. Любая цифра скорости в UI/README/маркетинге обязана иметь ссылку на строку в этом файле.

### 13.4 Паритет песочницы native ↔ research-Docker (замечание №5 ревью)

- **Единый источник политики:** `security/sandbox/policy.yaml` — allowlist путей, запрет сети, запрет exec, rlimits (CPU/RSS/FSIZE/NPROC), таймауты, лимиты пикселей/кадров/длительности.
- **Генераторы бэкендов из одного файла:** Linux seccomp+namespaces, macOS Seatbelt-профиль, Windows Job Object + restricted token, Docker-compose (read_only, cap_drop, `security_opt`, `network_mode: none`, `pids_limit`, `mem_limit`).
- **Тест `test_sandbox_policy_parity`** сравнивает эффективные лимиты native и Docker и падает при расхождении.
- **Нативные прогоны обязательны:** security-корпус (T01–T13) прогоняется на Windows, macOS и Linux как релизный гейт. Docker-прогон — дополнительный, с обязательной пометкой **research-only** в отчёте.
- **Запрещено** публиковать метрики продукта (ASR, sandbox escape, zero-egress), полученные только в Docker: они не воспроизводят условия Windows/macOS.
- `security/tests/README.md` фиксирует это правило, чтобы исследователь не сделал ложный вывод о защищённости продукта.

## 15. Бета-тест v0.1 в сообществе

**Набор:** 20–50 участников; все 3 ОС; ≥ 5 с архивом > 100k файлов; ≥ 5 видеографов; ≥ 3 «непрокачанных» пользователя (проверка UX); **≥ 3 на слабых CPU-only ноутбуках (8 ГБ, 4 ядра)** — они проверяют честность Lite и ночной задачи; **≥ 2 с архивом 200K+** — проверяют масштаб поиска.

**Условия входа (бета-соглашение):** работаем на копии или в режиме `copy`; у участника есть бэкап (спрашиваем явно); продукт ничего не удаляет; откат доступен; телеметрия и краш-репорты — opt-in, без содержимого файлов и PII; известные ограничения перечислены честно.

**Метрики беты:** время до первого результата; скорость на 10k файлов; доля правильно разложенного по мнению владельца; precision@5; доля ручной правки; crash-free ≥ 99%; обращений в саппорт на пользователя; SUS ≥ 70; **точность ETA VLM; число сообщений о «пропавшем семантическом поиске»; число инцидентов с осиротевшими процессами; латентность поиска на 200K+**.

**Артефакты:** `BETA_GUIDE.md` (10 минут), **`KNOWN_LIMITATIONS.md`** (обязательный, см. §16), шаблон баг-репорта (авто-сбор ОС/версий/профиля/бэкенда индекса без медиа), канал (Telegram/Discord + GitHub Issues), еженедельный дайджест, публичный roadmap, `SECURITY.md` (ответственное раскрытие).

**Выход из беты (критерии v0.2):** 0 инцидентов потери данных; crash-free ≥ 99%; ≥ 70% участников продолжают пользоваться через 2 недели; целевые метрики качества достигнуты; **0 инцидентов осиротевших процессов; 0 немотивированных деградаций поиска**.

- **Свойства ОС:** xattr/теги теряются на FAT/exFAT и при копировании через некоторые облака.

### 20.4 Уточнения сверх ревью (добавлено по итогам проверки источников)

1. **GPU-бюджеты тоже были оптимистичны.** Ревью указало на CPU; при проверке выяснилось, что и «Metal/CUDA 0.3–1 с/кадр» неверно для нового кадра: стоимость доминируется vision-encode (публичные замеры Qwen3-VL-2B — секунды на forward с изображениями даже на топовых GPU, и сотни миллисекунд без изображения). Дешёвый follow-up по тому же кадру — не показатель для продукта.
2. **Формулировка про sqlite-vec уточнена.** Автор расширения описывает его как **brute-force без ANN** (ANN — в roadmap), а сторонние замеры показывают конкурентоспособность на ~100K и резкую деградацию за ~1M. Поэтому в v3 порог 50–100K — это **инженерный порог переключения по латентности**, а не «жёсткий лимит работоспособности»; проверяется спайком E.
3. **Добавлены NFR-16…20 и SEC-17** — измеримые требования к старту/завершению sidecar, масштабу поиска, честности ETA и отзывчивости UI при фоновом VLM: без них правки остались бы декларациями.
4. **FR-2.13** — правила, зависящие от VLM, не должны ломать раскладку на профиле без VLM (следствие удаления VLM из Lite, которое ревью не проговаривало).

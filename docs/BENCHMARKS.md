# BENCHMARKS — единственный источник цифр скорости для UI

Правило: любая цифра скорости в UI, README или маркетинге обязана ссылаться на
строку этого файла или на замер `device_bench` на конкретном устройстве. Таблица
§8.3 ТЗ — **ожидание для планирования**, а не обещание.

## Как воспроизвести

```bash
kadr bench /path/to/library --limit 100 --output bench.json
kadr doctor
```

`kadr bench` пишет JSON: устройство, ОС, версии, профиль, файлы/с, эмбеддинги/с,
размер каталога. Результаты M0/M2 добавляются сюда вместе с релизом.

До заполнения этих строк UI показывает диапазон из §8.3 с явной пометкой
«ожидание», а не «замерено».

**Вывод по гейту E (§14):** sqlite-vec подтверждён до 100K (141 мс, recall 1.00),
поэтому порог переключения на ANN — **выше 100K** (`factory.auto_backend`).
ANN на дефолтах давал recall 0.31–0.61; после тюнинга conn32/ef200/256 —
0.915–0.99 на 10–50K, но **0.80 на 100K** (ниже NFR-18 ≥0.90). Вывод: для
100K использовать sqlite-vec; перед переходом на 200K — дотюнить ANN
(ef_search 512+) или выбрать иной ANN, иначе NFR-18 не выполняется (ADR-0004).

# ADR-0004: Сменный `VectorIndex` и порог переключения бэкендов

- **Статус:** принято (2026-11-15)
- **Контекст:** sqlite-vec 0.1.x — brute-force-поиск, а не ANN; комфортная зона — примерно до 50–100K векторов. Целевой архив — 200K+ файлов и ключевых кадров. Синтаксис KNN (`k = ?`) менялся между версиями, расширение требует `enable_load_extension`. Тихое падение семантического поиска недопустимо (FR-3.13/NFR-18).

## Решение

1. Домен обращается к векторам **только** через `kadr.vector.base.VectorIndex`; SQL к `vec0` вне адаптера запрещён.
2. Бэкенды:
   - `sqlite-vec` — M0 по умолчанию, версия пинится, есть smoke-тест;
   - `ann` — usearch/HNSW для > 100K;
   - `hybrid` — FTS5/метаданные сужают кандидатов, затем точный реранк эмбеддингами (50–100K+);
   - `brute-force` — явный fallback без расширений.
3. Автовыбор по числу векторов: ≤ 50K — `sqlite-vec`; 50–100K — `hybrid`; > 100K — `ann`. Ручной override сохраняется в `settings.vector_backend_override`.
4. Эмбеддинги хранятся в `embeddings` независимо от индекса. Пересборка индекса (`kadr reindex`) **не пересчитывает** эмбеддинги и не удаляет их.
5. Любая недоступность/ошибка бэкенда записывается в `vector_index_state.status = degraded|unavailable` с `reason`. UI/CLI показывают бейдж; поиск продолжает работать через FTS5/структурные фильтры.
6. `index_generation` меняется при смене модели/размерности; старый индекс обслуживает поиск до готовности нового.

## Результаты спайка E (2026-11-20, Windows 11 / 28 ядер, dim=128, синтетика)

Замерено `tests/scale/bench_scale.py` (recall@10 против точного перебора):

| Векторов | sqlite-vec p95 | sqlite-vec recall | ann (tuned) p95 | ann recall | Статус |
|---|---|---|---|---|---|
| 10K | 13 мс | 1.00 | 4,3 мс | 0.99 | замерено |
| 50K | 54 мс | 1.00 | 7,3 мс | 0.915 | замерено |
| 100K | 141 мс | 1.00 | измеряется | измеряется | sqlite-vec подтверждён |

Выводы:

1. **sqlite-vec держит 100K лучше, чем предполагалось** в v3 (§9 «~50–100K»): p95 141 мс при цели NFR-18 ≤ 300 мс, recall 1.00. Комфортная зона — как минимум до 100K.
2. **usearch на дефолтных параметрах не проходит NFR-18**: recall@10 = 0.31–0.61 (connectivity 16, expansion_search 64). После тюнинга **connectivity=32, expansion_add=200, expansion_search=256** — recall@10 0.915–0.99 при 4–7 мс (зафиксировано в `kadr/vector/ann_usearch.py`).
3. **hybrid пока не ANN и не сужение**: это точный Python-перебор (~450 мс уже на 10K), FTS5-сужение ещё не реализовано. До M2 hybrid не выбирается автоматически.
4. **Порог переключения уточнён по данным**: sqlite-vec до 100K, tuned-ANN выше (`factory.auto_backend`). Прежний порог 50K→hybrid отменён как преждевременный.
5. **Найден и исправлен квадратичный дефект сборки**: `record_status()` вызывался на каждую вставку и считал COUNT(*) по vec0 → 50K строились 306 с, 100K не завершались. После переноса статуса в `add_many()` — 22 с (50K), 44 с (100K).

## Последствия

- На машинах без sqlite-vec поиск работает, но деградация видима, а не «молчаливая».
- ANN-бэкенд проверяется спайком E на 50K/100K/200K/500K; до подтверждения NFR-18 порог остаётся инженерным.
- Ограничение brute-force зафиксировано в [`KNOWN_LIMITATIONS.md`](../../KNOWN_LIMITATIONS.md) и `docs/THREAT_MODEL.md`.

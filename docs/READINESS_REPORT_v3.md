# Отчёт о готовности: ТЗ v3 (Kadr / MIAS) и репозиторий

**Дата:** 2026-11-20
**Объект:** `docs/spec/v3.md` (977 строк, 135 664 байта, редакция «3.0-draft» от 2026-11-13) и фактическое состояние репозитория: ветка `main`, HEAD `368346c`, рабочее дерево грязное — см. BLK-11 и Приложение B.

## 1. Вердикт

> **Документ можно брать в работу — после 14 правок (v3.1). Продукт к собственному DoD M0 не готов: 3 из 5 блокирующих спайков не пройдены, 2 обязательных PR-гейта красные, 3 (на дефолтной консоли Windows — 4) теста падают.**
>
> Сильная сторона проекта не там, где ожидается по ТЗ: **движок раскладки (M1) уже реализован на ~80%** — это лучший актив и его не надо переделывать. Слабая — **UI-оболочка, дистрибуция и измерения**: M4/M6 фактически не начаты, а «честность цифр», на которой держится вся концепция v3, пока не подкреплена ни одним замером.

|---|---|---|

### 1.1 Пять выводов

1. **Спецификация зрелая.** 55 FR, 20 NFR, 17 SEC, 13 решений, ADR-0001…0005, гейты, KNOWN_LIMITATIONS, разделение «код/веса», видимая деградация поиска. Все 41 внутренняя `§`-ссылка резолвятся (кроме `§3.5` — это раздел чужого документа `docs/PROPOSAL.md`, и `§18.10` — пункт списка открытых вопросов).
2. **Реализация не соответствует своему же отчёту.** `STATUS.md` ставит «✅ Тесты», «✅ VectorIndex и видимая деградация»; фактически тесты красные, а sqlite-vec не загружается даже там, где расширение установлено (BLK-01).
3. **Механизм «проверки вместо обещаний» создан, но не работает.** Скрипты-гейты написаны (`scripts/*.py`) и подключены к CI, но два из них физически не могут стать зелёными (BLK-01, BLK-02). Это хуже отсутствия гейтов: красный гейт приучает игнорировать красное.
4. **Главный риск проекта — не VLM и не векторы, а UI.** M4+M6 = 6–8 выходных и вся связка Tauri↔Python (§11.2) не проверена ни разу. В ТЗ этот риск стоит №4, по факту он №1.
5. **«Честность» продукта (главная идея v3) пока декларативна.** Ни одна цифра §8.3 не заменена замером, golden-датасета нет, метрик качества нет. До спайков D/E любое UI-число — запрещённая по ТЗ константа.

## 4. Блокеры

Приоритет: **BLK-01…BLK-03 — не начинать M1+ до закрытия** (красные гейты + дефекты в core). **BLK-04…BLK-06 — блокирующие гейты M0** (требуют железа). **BLK-07…BLK-11 — блокируют M4–M6.**

### BLK-01. sqlite-vec не загружается через адаптер → семантический поиск «деградирован» на машинах, где расширение установлено

- **Симптом:** `sqlite_vec_smoke.py` даёт `available=false, status=degraded, reason="sqlite_vec.load failed: not authorized"` при установленном `sqlite_vec` 0.1.9.
- **Доказательство:** прямой опыт — `conn.enable_load_extension(True); sqlite_vec.load(conn)` → `vec_version()=v0.1.9`; адаптер `kadr/vector/sqlite_vec.py:32` вызывает `sqlite_vec.load(conn)` **без** `enable_load_extension(True)` (это делается только в ветке `KADR_SQLITE_VEC_PATH`, строка 43).
- **Влияние:** гейт `sqlite-vec-smoke` (§12.3) красный на всех 3 ОС всегда, когда расширение установлено; спайк A не пройден; NFR-18 недостижим; FR-3.1/FR-3.13 выполнены только формально.
- **Действие:** включить загрузку расширений на соединении каталога (и выключать после), добавить тест «если `sqlite_vec` импортируется — бэкенд обязан быть `active`», иначе тест падает (а не skip).
- **Оценка:** 0,5–1 ч.

### BLK-02. Гейт `sidecar-lifecycle` красный на Windows из-за неверной проверки живости

- **Симптом:** `check-sidecar-lifecycle.py` → `exit 1`, `{"name":"process_group_shutdown","alive":[<pid>]}`, стабильно 3/3.
- **Доказательство:** отладочный прогон: `taskkill /PID … /T /F` → `rc=0`, `process.poll()=1`, но `wait_for_no_orphans()` навсегда возвращает PID. Причина — `kadr/lifecycle.py:336`: `os.kill(pid, 0)` на Windows не является проверкой существования (для не-сигнальных значений `os.kill` вызывает `TerminateProcess`, а `OpenProcess` по PID завершённого, но не «переиспользованного» объекта может успешно открываться, пока жив handle в `Popen`).
- **Влияние:** SEC-17/NFR-17 не подтверждены; PR-гейт красный; сам `terminate_group` в этом сценарии корректен — дефект в измерителе, но гейт от этого не зеленеет.
- **Действие:** заменить проверку на `psutil.pid_exists()`/Win32 (`OpenProcess` + `GetExitCodeProcess == STILL_ACTIVE`) или на `process.wait(timeout)` + опрос группы; расширить скрипт до сценариев §11.2.3 (`prevent_exit`+`exit()`, Cmd+Q/`MenuItem::Quit`, kill -9 UI, logout, updater-restart, «внуки»).
- **Оценка:** 1–1,5 дня (вместе с расширением матрицы сценариев — это и есть спайк B).

### BLK-03. Падающие тесты: 3 (4 на дефолтной консоли Windows)

| Тест | Причина | Класс |
|---|---|---|
| `test_api_security::test_auth_required_and_csrf_for_mutations` | Тест ждёт 200/400 для `root=/tmp`, а API возвращает 403 из allowlist корней (`security/paths.py:158`). Тест устарел после ужесточения | тест |
| `test_paths_security::test_symlink_component_is_rejected` | `OSError WinError 1314` — на Windows без `SeCreateSymbolicLinkPrivilege` symlink не создаётся. Нужен `skipif`/Developer Mode | тест/CI |
| `test_xmp_privacy::test_embedded_write_preserves_exif_icc_and_returns_backup` | `kadr/xmp.py:415`: `os.fsync()` на дескрипторе, открытом в `"rb"` → `OSError [Errno 9] Bad file descriptor`. Это **реальный дефект** атомарной записи (SEC-13, FR-4.3) | код |
| `test_kadr_cli::…` (только без UTF-8) | CLI печатает не-ASCII при `ensure_ascii=False` → `UnicodeEncodeError` на cp1251-консоли. Реальный дефект Windows (NFR-14, §16 п.5) | код |

- **Влияние:** джоб `tests` красный; SEC-13 и FR-4.3 не подтверждены; Windows-first аудитория (NFR-14) получает падающий CLI.
- **Действие:** починить `xmp.py` (fsync на `rb+`/открывать `wb` заново), `sys.stdout.reconfigure(encoding="utf-8", errors="replace")` в `cli.main`, поправить два теста, добавить маркер `windows_symlink`.
- **Оценка:** 1 день.

### BLK-04. Спайк D (VLM-бюджеты) не выполнен — DoD M0 недостижим

- **Симптом:** `docs/BENCHMARKS.md` — 4 строки «не измерено (ожидание …)»; манифест весов: 4 записи `enabled: false, revision: null, license_verified_at: null`; VLM-код — контракт + HTTP-клиент к `llama-server`, рантайм не запускался.
- **Влияние:** §8.3 остаётся «ожиданием»; риск №1 не снят; UI не имеет права показывать цифры; ночная задача (FR-3.14) не может быть ни включена, ни оценена.
- **Действие:** 4 класса устройств × 2 разрешения × thinking on/off; результат в `BENCHMARKS.md` + `device_bench`; при > 25 с/кадр на 4 ядрах — гейт §14 (только выборка, а не весь архив).
- **Оценка:** 2–3 дня календарно (нужны машины; GPU можно арендовать).

### BLK-05. Спайк E (масштаб 50K–500K) не выполнен

- **Симптом:** `tests/scale/` содержит только README; `usearch` не установлен; `ann_usearch.py` не запускался; p95/recall@10/размер БД не измерены; порог переключения бэкендов (50K/100K) — инженерная гипотеза.
- **Влияние:** NFR-18 не подтверждён; риск №2 открыт; DoD M2 («scale-тест на 200K проходит NFR-18 выбранным бэкендом») недостижим.
- **Действие:** синтетические наборы 50/100/200/500K, замер p95/recall@10/размера, выбор бэкенда, фиксация порога в ADR-0004.
- **Оценка:** 2–3 дня.

### BLK-06. Спайк C (PyInstaller one-dir) не измерен

- **Симптом:** `packaging/kadr-engine.spec` есть, `check-no-onefile.py` зелёный, но PyInstaller не в зависимостях, сборка не выполнялась, холодный/повторный старт и размер не замерялись, SmartScreen/антивирусы не проверялись.
- **Влияние:** NFR-07 (≤ 60 МБ), NFR-16 (≤ 2 с) не подтверждены; риск №4 (Tauri+Python) не снят.
- **Действие:** собрать one-dir на 3 ОС, замерить старт/размер, проверить поведение при завершении, переименование под target-triple, прогон в чистой VM.
- **Оценка:** 2 дня.

### BLK-07. UI-оболочка отсутствует: нет `ui/`, нет `tauri.conf`, не выбран фреймворк

- **Симптом:** в репозитории нет Tauri-приложения, нет `packaging/tauri.conf`, нет capabilities, нет lifecycle-хуков Rust (`RunEvent::Exit`); UI — `kadr/static/index.html` (1,4 КБ) + `ui.js` (2,4 КБ).
- **Влияние:** FR-5.1–5.8, FR-2.12 не выполнены; NFR-05/NFR-10 не проверяемы; §11.2 (Tauri↔sidecar) не проверен в реальной связке; DoD M0 «выбор UI-фреймворка» не выполнен; M4 и M6 не начаты.
- **Действие:** решение по фреймворку (Svelte vs React) — 1 день прототипом; каркас Tauri 2 + sidecar-handshake + `app_shutdown()`.
- **Оценка:** каркас 2–3 дня; полный M4 — см. план.

### BLK-08. CI не соответствует §12.3 и §6.2

- **Отсутствуют джобы:** `license-code` (SBOM, `pip-audit`/`osv-scanner`, `cargo-deny`, Trivy), `sandbox-parity` (скрипт есть — джоба нет), SAST, SBOM-diff.
- **Не запускаются** `ruff` и `mypy`, хотя заявлены в стеке §6.2 и стоят в `[dev]`.
- **Дублирование:** `.github/workflows/python-tests.yml` (только Ubuntu) и `kadr-ci.yml` (`tests`, матрица 3 ОС) прогоняют одно и то же; `python-tests.yml` ставит `ffmpeg`, а `kadr-ci.yml` — нет, поэтому окружения тестов расходятся.
- **Слабые гейты:** `license-weights` зелёный только потому, что все веса `disabled` — ни одна включённая модель через него ещё не проходила; `check-sandbox-parity.py` проверяет проектный паритет политики и наличие реального `setrlimit`, но не enforcement (seccomp/Seatbelt/Job Object — «M3»); `check-spec-invariants.py` падает на не-UTF-8 консоли (`UnicodeEncodeError`) и не проверяет `v2.md`.
- **Оценка:** 1–2 дня.

### BLK-09. Нет golden-датасета и метрик качества (§13.2)

- **Симптом:** нет `tests/golden/`; ни одна из 11 целевых метрик (99% «по дате», precision@5, nDCG@10, CER, WER, recall@10, ±30% ETA) не измеряется; `security/corpus/` и `security/redteam/` — только README.
- **Влияние:** DoD M2 и M3 недостижимы; заявления «видимая деградация», «PII 0 в stock» не проверяемы; §9 целевые метрики (ASR инъекций 0%) не измеряются.
- **Действие:** собрать 500–1000 файлов с протоколом разметки (кто, как, версия), харнесс метрик, каталог инъекций T01–T03.
- **Оценка:** 3–4 дня (данные — самый длинный «человеческий» полюс).

### BLK-10. Песочницы ОС не реализованы (только rlimits), парсер-воркер — единственный

- **Симптом:** `security/sandbox/policy.yaml` есть, но генераторов seccomp/Seatbelt/Job Object нет; `kadr/security/sandbox.py` — POSIX rlimits/timeout; parser-worker один; нет ai-worker/vlm-worker как процессов; egress enforcement отсутствует; `test_zero_egress`, `test_sandbox_escape`, `test_malformed_corpus`, `test_sandbox_policy_parity` отсутствуют.
- **Влияние:** SEC-05/09/12 не выполнены; M3 не начат; §13.4-паритет не проверяется.
- **Оценка:** M3 — см. план (3–4 дня только на песочницы + 2–3 на корпус).

### BLK-11. Гигиена репозитория и управление версиями спеки

- **Симптом:** грязное дерево: 4 файла `.github/workflows/attack_surface/*.py` удалены, но не закоммичены; неотслеживаемый `.pytest-junit.xml`; мусор в дереве: `docs/d6f1e985…` (0 байт), `docs/spec/test_file.txt`, `test_edit.txt`, `attack_surface/tmp_test.py`, `attack_surface/.tmp_file`, `attack_surface/.api.py.gku1ccm4.tmp`, четыре `Modelfile-*` в корне, логи pytest в корне.
- **Влияние:** `git status` не чист → нельзя строить «релиз = коммит»; link-checker и spell-check ругаются на мусор; новый контрибьютор не понимает, что живо, а что наследие PoC.
- **Действие:** единый коммит «cleanup» (удаление `.github/workflows/attack_surface`, мусорных файлов, перенос логов в `.gitignore`), правило «PR не начинается с грязного дерева».
- **Оценка:** 0,5 дня.

## 7. Что сделано хорошо (не переделывать)
